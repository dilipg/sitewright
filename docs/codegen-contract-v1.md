# Codegen Contract v1

Status: Draft for review
Scope: The binding contract between every code-generating agent, the canvas editor, the override layer, and the exporter. Everything else in the system (runtime, prompts, UI) depends on this document and must not violate it.

---

## 1. Purpose and non-goals

This contract exists so that:

1. Code generated by parallel agents composes into one coherent project with zero merge conflicts by construction.
2. Every visual element the canvas shows can be addressed by a stable ID, so user edits can be stored as patches and compiled into source at export.
3. A section can be regenerated in isolation (via runtime replay) without invalidating user edits elsewhere.
4. Exported code is developer-handover quality: typed props, mock data at clear seams, direct component imports.

Non-goals for v1: business logic, backend integration, live bidirectional code editing, multi-theme creativity variance, CMS integration.

---

## 2. Project layout (fixed, agents may not deviate)

```
project/
  src/
    tokens/
      tokens.json            # design tokens, single source of truth
      tokens.css             # generated CSS custom properties, derived only
    primitives/              # generated once by the Design System Agent
      Button.tsx
      Card.tsx
      Input.tsx
      Heading.tsx
      Text.tsx
      ...
    shell/                   # generated once by the Shell Agent
      AppShell.tsx           # layout frame: nav + outlet + footer
      Nav.tsx
      Footer.tsx
      routes.ts              # route table, ground truth for all links
    pages/
      <route-slug>/          # one directory per route, one page agent owns it
        index.tsx            # page assembly only, no styling decisions
        sections/
          <SectionName>.tsx  # one file per section
        mock/
          <SectionName>.data.ts
    lib/
      types.ts               # shared prop and data types
  overrides/
    <route-slug>.overrides.json   # canvas edit patches, never touched by agents
  manifest.json              # node registry, see section 5
```

Ownership rules:

- The Design System Agent is the only writer of `tokens/` and `primitives/`.
- The Shell Agent is the only writer of `shell/`.
- A page agent writes only inside its own `pages/<route-slug>/` directory.
- No agent ever writes to `overrides/`. Only the editor does.
- `manifest.json` is append-and-update via the manifest service (section 5.4), never freehand.

These rules make write contention impossible rather than resolved.

## 3. Design tokens

### 3.1 tokens.json schema

```json
{
  "version": 1,
  "meta": { "themeName": "string", "generatedAt": "ISO-8601" },
  "color": {
    "primary": { "50": "#...", "100": "#...", "...": "#...", "900": "#..." },
    "neutral": { "...": "..." },
    "semantic": {
      "bg": "ref:color.neutral.50",
      "surface": "ref:color.neutral.100",
      "text": "ref:color.neutral.900",
      "textMuted": "ref:color.neutral.600",
      "accent": "ref:color.primary.600",
      "accentContrast": "#ffffff",
      "border": "ref:color.neutral.200",
      "danger": "#...",
      "success": "#..."
    }
  },
  "typography": {
    "fontFamily": { "heading": "string", "body": "string", "mono": "string" },
    "scale": { "xs": "0.75rem", "sm": "0.875rem", "base": "1rem", "lg": "1.125rem", "xl": "1.25rem", "2xl": "1.5rem", "3xl": "1.875rem", "4xl": "2.25rem", "5xl": "3rem" },
    "weight": { "regular": 400, "medium": 500, "semibold": 600, "bold": 700 },
    "leading": { "tight": 1.15, "snug": 1.3, "normal": 1.5, "relaxed": 1.7 }
  },
  "space": { "0": "0", "1": "0.25rem", "2": "0.5rem", "3": "0.75rem", "4": "1rem", "6": "1.5rem", "8": "2rem", "12": "3rem", "16": "4rem", "24": "6rem" },
  "radius": { "none": "0", "sm": "0.25rem", "md": "0.5rem", "lg": "1rem", "full": "9999px" },
  "shadow": { "sm": "...", "md": "...", "lg": "..." },
  "breakpoint": { "sm": "640px", "md": "768px", "lg": "1024px", "xl": "1280px" }
}
```

`ref:` values are resolved when `tokens.css` is generated. Semantic tokens are the only tokens components may reference for color.

### 3.2 Hard rules

- Components reference tokens exclusively through CSS custom properties (`var(--color-semantic-accent)`, `var(--space-4)`) or the Tailwind theme mapping generated from tokens.json. Never raw hex, never raw px for spacing.
- Page agents receive tokens.json read-only in their context. They may not add, rename, or re-derive tokens.
- If a page agent needs a value that has no token, it must use the nearest existing token. Escape hatches are a lint failure (section 8).
- v1 creativity setting is fixed low: page agents make layout and copy decisions only. All style decisions live in tokens and primitives.

## 4. Primitives and components

### 4.1 Primitive set (generated once, before any page agent runs)

Minimum v1 set: `Button`, `Card`, `Input`, `Textarea`, `Select`, `Badge`, `Heading`, `Text`, `Link`, `Image`, `Container`, `Grid`, `Stack`, `Divider`, `Icon`.

Each primitive:

- Is a typed functional component with an exported props interface named `<Name>Props`.
- Accepts `nodeId?: string` and spreads it as `data-node-id` on its root element (see section 5).
- Accepts `className?: string` merged last, so override compilation can inject classes.
- Has variants expressed as a `variant` prop with a closed union type, not free-form styling props.

### 4.2 Section components

A section is the unit of generation, regeneration, checkpointing, and editing scope. Rules:

- One section = one file = one exported component + one exported props interface + one mock data file.
- Sections compose primitives; they may define local sub-components inside the same file but may not create new files outside their page directory.
- Sections must not import from another page's directory. Shared needs escalate to primitives, which only the Design System Agent may add between generation waves (never concurrently with page agents).

### 4.3 Props and mock data seam

This is the developer-handover contract:

```tsx
// sections/PricingTiers.tsx
export interface PricingTiersProps {
  heading: string;
  tiers: Array<{ name: string; price: string; features: string[]; cta: { label: string; href: string } }>;
}
export default function PricingTiers({ heading, tiers }: PricingTiersProps) { ... }
```

```ts
// mock/PricingTiers.data.ts
import type { PricingTiersProps } from "../sections/PricingTiers";
export const pricingTiersData: PricingTiersProps = { ... };
```

```tsx
// index.tsx assembles: <PricingTiers nodeId="..." {...pricingTiersData} />
```

Rules:

- Zero user-visible strings hardcoded inside section components. All content flows through props; all props are satisfied by mock data files. A developer replaces the mock import with an API call and the component is production-usable unchanged.
- All interactive elements that would need business logic (form submit, add to cart, auth) receive a handler prop typed in the props interface, wired in mock data to a no-op with a `// TODO: integrate` comment. This is the explicit seam for the "frontend only" scope.
- Links use `href` values that exist in `shell/routes.ts` or are explicitly external. Page agents receive the route table read-only.

## 5. Node identity (the load-bearing part)

### 5.1 What gets a node ID

Every element the canvas editor allows a user to select: every section root, every primitive instance, and every direct semantic child an editor gesture could target (headings, paragraphs, images, buttons, grid cells). Purely structural wrappers do not need IDs.

### 5.2 ID format

```
<route-slug>.<section-slug>.<element-path>
e.g.  home.hero.headline
      home.hero.cta-primary
      pricing.tiers.tier-1.cta
```

Rules that make IDs stable:

- IDs are semantic, not positional. `home.hero.cta-primary`, never `home.hero.child-3`. Positional IDs break on regeneration; semantic IDs survive it.
- IDs are assigned by the generating agent at generation time and emitted both as `data-node-id` attributes and as entries in `manifest.json`.
- List items generated from mock data arrays derive IDs from stable keys in the data (`tier-1` from `tiers[0].name` slug), rendered via the `nodeId` prop inside the map.
- IDs are immutable once registered. A regenerated section must reuse the IDs of any element that survives conceptually (the headline is still the headline). New elements get new IDs; removed elements get their manifest entries tombstoned.

### 5.3 Regeneration and ID survival

When a section is regenerated (runtime replay with modified prompt), the section agent receives: the old section source, the manifest entries for that section, and the list of node IDs that currently have user overrides. The prompt instructs: preserve every overridden node ID whose element still exists; if the regeneration removes an overridden element, list its ID in the response metadata as `orphanedOverrides`. The editor then surfaces orphaned edits to the user instead of silently dropping them. This rule is why edits survive regeneration, and it must be enforced by the post-generation validator (section 8), not trusted to the prompt.

### 5.4 manifest.json

The node registry, maintained through a small deterministic service (not by LLM freehand):

```json
{
  "version": 1,
  "nodes": {
    "home.hero.headline": {
      "route": "/",
      "file": "src/pages/home/sections/Hero.tsx",
      "component": "Hero",
      "element": "Heading",
      "editable": ["text", "typography", "spacing", "color"],
      "status": "active"
    }
  }
}
```

`editable` declares which override channels the editor may offer for this node. Agents propose manifest entries in structured output; the manifest service validates uniqueness, format, and tombstone rules, then commits. This keeps the registry consistent even when an agent misbehaves.

## 6. Override layer

### 6.1 Schema

One file per route, owned exclusively by the editor:

```json
{
  "version": 1,
  "route": "/",
  "overrides": [
    {
      "nodeId": "home.hero.headline",
      "channel": "text",
      "value": "Ship your storefront in a weekend",
      "updatedAt": "ISO-8601"
    },
    {
      "nodeId": "home.hero.cta-primary",
      "channel": "style",
      "value": { "marginTop": "space.8", "background": "color.semantic.accent" },
      "updatedAt": "ISO-8601"
    },
    {
      "nodeId": "home.hero.image",
      "channel": "layout",
      "value": { "width": "480px", "alignSelf": "center" },
      "updatedAt": "ISO-8601"
    }
  ]
}
```

Channels for v1: `text` (content replacement), `style` (token-referencing style deltas), `layout` (size and position deltas from drag/resize gestures), `visibility` (hide element). One entry per node+channel; later edits replace earlier ones, so files stay small and export is idempotent.

Style values reference tokens where possible (`space.8`); the editor snaps gestures to the token scale by default with a free-value escape the user must deliberately choose. This keeps user edits inside the design system, which keeps exported code clean.

### 6.2 Preview semantics

The canvas preview applies overrides at render time: text channel via a content map consumed by a small runtime shim, style/layout channels via injected classes keyed by `data-node-id`. No code files are modified during editing. This is what makes editing instant and generation-independent.

## 7. Export compilation

Export produces the handover artifact: the generated source with all overrides compiled in and the override files consumed.

Deterministic pipeline, no LLM in the loop for steps 1 to 4:

1. **Text channel**: locate the prop value or mock data field feeding the node (via manifest file + component mapping) and rewrite the mock data literal. Text edits land in data files, not JSX, preserving the props seam.
2. **Style and layout channels**: resolve token references to Tailwind classes (or CSS custom property utilities) and merge them into the node's `className`, last position. Free values compile to arbitrary-value classes.
3. **Visibility channel**: remove the element's JSX and tombstone its manifest entry.
4. **Verification build**: run typecheck, lint (section 8), and a production build. Export fails loudly on any error; a failed export never ships silently degraded code.
5. **LLM cleanup pass (optional, flagged)**: a single low-cost pass that renames awkward compiled classes into tidier form. Off by default in v1; determinism beats polish.

Post-export, override files are archived, not deleted, so the user can trace what changed.

---

## 8. Validation gates (mechanical, run after every agent and before export)

1. All imports resolve; build passes.
2. Every `href` exists in `routes.ts` or is whitelisted external.
3. No raw hex colors or raw px spacing outside `tokens/` (regex + AST lint).
4. Every selectable element carries a `data-node-id` present in the manifest; no duplicate IDs.
5. No user-visible string literals inside section JSX (all content via props).
6. No cross-page imports; no agent wrote outside its ownership boundary (checked via file diff against the ownership map).
7. On regeneration: every previously overridden node ID is either present in output or declared in `orphanedOverrides`.

A gate failure triggers a bounded retry from the section's checkpoint with the failure message appended to the prompt (max 2 retries, then surface to user). Gates are cheap code, not LLM calls, in line with the token conservation constraint.

## 9. Agent interface summary (what each agent receives and must emit)

| Agent | Reads | Writes | Emits (structured) |
|---|---|---|---|
| Design System Agent | user brief | tokens/, primitives/ | token summary, primitive inventory |
| Shell Agent | brief, tokens, primitive inventory | shell/ | route table, nav map |
| Page Agent (per route) | brief, tokens (RO), primitive inventory (RO), route table (RO), archetype template | pages/<slug>/ only | manifest entry proposals, section list |
| Regeneration run | above + old source + section manifest + overridden ID list | its section files only | manifest updates, orphanedOverrides |

Checkpoint boundaries (Kitaru): one checkpoint per section generation, one per validation gate result. Replay-with-overrides targets a single section checkpoint with a modified instruction, which is the "redo just the pricing section" feature.

---

## 10. Open items (deliberately deferred, do not solve in v1)

- Responsive overrides (per-breakpoint edit values); v1 edits apply to desktop, generation handles responsiveness.
- Multi-theme or high-creativity variance across pages.
- Component-level extraction of repeated user edits ("you styled 5 buttons the same way, update the primitive?").
- Live collaborative editing.
