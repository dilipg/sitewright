# Job Model (slice 5) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every long-running operation becomes a job: enqueued, worked server-side, polled by the browser — and web-triggered generation exists for the first time.

**Architecture:** A job is a **server-side wrapper around the same work the server already performs**. Five kinds replay a proxied request to the project's preview child, which stays synchronous and unchanged; `generate` spawns the orchestrator directly, because there is no site for a Vite child to serve until it has run. One SQLite table, one in-process worker loop, polling for progress.

**Tech Stack:** Node 24, `node:sqlite`, TypeScript, vitest. No new runtime dependencies, no queue library, no second process.

## Context

Read first: **`docs/superpowers/specs/2026-08-06-job-model-design.md`** — the approved design, including the three human decisions (SQLite table, convert every long-running operation, polling), the resolved project-at-enqueue question, and the named accepted losses. It supersedes nothing; it retires the deferral that the accounts spec's decision 11 made deliberately.

Also read `docs/decisions.md`'s 2026-08-05 and 2026-08-06 rows — several bind this work directly, especially the exactly-once ingest placement and the key-fingerprint respawn.

**State you inherit.** Slices 2–4 are merged. `server/` has a deny-by-default route table, `requireSession`/`requireProject`/`requireBudget`, a preview pool (one child per project, capped at 6, reaped when idle, respawned when a key fingerprint goes stale), a proxy that no longer abandons an upstream on client abort, and all fifteen `/__*` endpoints mounted with spend attributed per billable request.

## Global Constraints

1. **No route may create a user.** `server/src/user-cli.ts` stays the only path. `POST /api/generate` creates a *project*, never an account.
2. **Deny by default.** Every endpoint is in exactly one `project-registry.ts` list with its flags; the lists stay a partition of `buildRoutes`'s live output. The registry's billable-enforcement table already iterates **both** lists — the session-only branch exists precisely for `POST /api/generate` and its visible skip should disappear when this lands.
3. **A job belonging to another user answers 404**, using the same shared constant `requireProject` uses. Job ids must not be an enumeration oracle any more than project ids are.
4. **The spend cap gates enqueue, never a running job.** A job that queues under the cap and finishes over it runs to completion — the spec accepts overshoot for one run.
5. **Ingest rules are relocated, not rewritten:** after the work, exactly once, then delete the file, in the same `finally` that frees the child and the slot, and **skipped when the exchange never completed**. `ingestUsageLog` is not idempotent.
6. **Nothing may log or persist API-key material.** `request_json` holds a route, a section id and an instruction — never a key. Child output goes through `redactSecrets`.
7. **A job left `running` across a restart becomes `interrupted` and is never retried.** The server cannot know whether the child finished; retrying would bill twice and could regenerate a section twice.
8. Migrations are append-only and idempotent. No new runtime dependencies. No platform-specific path literals in assertions (CI is ubuntu). Money is REAL USD.
9. **Every test must fail if the behaviour it names is removed.** Perturb, watch the named assertion fail, restore. **If a perturbation does not fail, say so rather than moving on** — that has produced five real findings across these slices.
10. **Never modify `docs/` to make code pass.**

### Task 1: The `job` table and its store

**Files:** modify `server/src/db.ts`; create `server/src/jobs.ts`, `server/src/jobs.test.ts`.

**Produces:**
- `type JobKind = "generate" | "regen" | "regen-page" | "add-section" | "edit-prompt" | "export"`
- `type JobStatus = "queued" | "running" | "succeeded" | "failed" | "interrupted"`
- `createJob(db, { userId, projectId, kind, requestJson, now }): Job`
- `findJobById(db, id): Job | null`
- `listJobsByProject(db, projectId, limit): Job[]`
- `countActiveJobsForUser(db, userId): number` — `queued` + `running`
- `claimNextJob(db, now): Job | null` — oldest `queued`, atomically flipped to `running`
- `finishJob(db, id, { status, resultJson?, error?, now }): void`
- `markRunningJobsInterrupted(db, now): number` — boot recovery

Append to `MIGRATIONS` (never reorder, never edit an existing entry):

```sql
CREATE TABLE IF NOT EXISTS job (
  id           TEXT PRIMARY KEY,
  user_id      TEXT NOT NULL REFERENCES user(id) ON DELETE CASCADE,
  project_id   TEXT REFERENCES project(id) ON DELETE SET NULL,
  kind         TEXT NOT NULL,
  status       TEXT NOT NULL,
  request_json TEXT NOT NULL,
  result_json  TEXT,
  error        TEXT,
  created_at   INTEGER NOT NULL,
  started_at   INTEGER,
  finished_at  INTEGER
)
```
```sql
CREATE INDEX IF NOT EXISTS job_user_status_idx ON job(user_id, status)
```

`project_id` is `ON DELETE SET NULL` like `usage_event`: deleting a project must not erase the record that work was paid for.

**`claimNextJob` must be atomic.** One worker loop exists today, but a second caller (a test, a future second worker) must not be able to claim the same row twice. Use a conditional update — `UPDATE job SET status='running', started_at=? WHERE id=(SELECT id FROM job WHERE status='queued' ORDER BY created_at LIMIT 1) AND status='queued'` — and return the row only if it changed. **Test it by claiming twice in a row and asserting the second call returns a different job (or null), never the same id.**

Tests to write first, each perturbation-provable: a created job is `queued` with no `started_at`; `countActiveJobsForUser` counts queued and running but not finished; `claimNextJob` returns the oldest first and never the same row twice; `finishJob` sets `finished_at` and the terminal status; `markRunningJobsInterrupted` converts only `running` rows and returns how many; a job survives its project being deleted, with `project_id` nulled.

Commit: `feat(server): record long-running work in a job table`.

### Task 2: The worker

**Files:** create `server/src/job-worker.ts`, `server/src/job-worker.test.ts`.

**Produces:** `class JobWorker` with `start()`, `stop()`, and `runOnce(): Promise<boolean>` — the last so tests drive one job deterministically instead of racing a timer.

The loop: claim a job, run it, finish it, repeat; sleep briefly when there is nothing to claim. `start()` arms an interval that must be `unref()`'d so it never holds the process open, and `stop()` must await an in-flight job rather than abandoning it.

**Two execution strategies behind one table** — state this in the module docstring rather than implying uniformity:

- **Proxied kinds** (`regen`, `regen-page`, `add-section`, `edit-prompt`, `export`): do exactly what `preview-forward.ts` does today — `pool.acquire`, `retain`, generate the usage id, `proxyHttp` the recorded body to the child, then in one `finally`: `release`, and ingest **only if the exchange completed**. Reuse `preview-forward.ts`'s pieces; do not re-derive them.
- **`generate`**: spawn the orchestrator directly with `buildAgentEnv`, `WEBGEN_USAGE_LOG` pointed at the job's own usage path, stdout/stderr through `redactSecrets`, then ingest under the same rules. There is no preview child to proxy to — the site does not exist yet.

**Bounds, enforced at claim time:** at most 2 active jobs per user (today's in-flight reservation, same value, same meaning), and the preview pool's cap of 6 doing double duty globally. A job that cannot run yet stays `queued` rather than failing — better than today's 503.

Tests: a proxied job calls the pool and the proxy with the recorded body; a failed proxy marks the job `failed` with a redacted error and still releases; ingest happens for a completed exchange and is skipped for an incomplete one; the per-user bound leaves a third job `queued`; `stop()` waits for the running job.

Commit: `feat(server): work jobs off the queue with the reviewed spend rules`.

### Task 3: Endpoints, registry, and boot wiring

**Files:** create `server/src/job-routes.ts` + test; modify `server/src/compiler-routes.ts`, `server/src/project-registry.ts` (+ test), `server/src/compose.ts` (+ test), `server/scripts/serve.ts`.

**The registry gains a required `async: boolean`** on every entry, for the same reason `billable` is required: omitting it must be a compile error, not something a reviewer notices. `async: true` on the six job kinds, `false` on everything else.

**New endpoints:**
- `POST /api/generate` — session-only, `billable: true`, `async: true`. Validates the brief, **creates the project row and its directory**, then enqueues. Returns **202 `{ jobId, projectId }`**.
- `GET /api/jobs/:id` — session-only. Owner-checked on the **job's own `user_id`**, not its project, because that is what a generation job has. Foreign or absent → **404**, one branch, one shared constant.
- `GET /api/jobs?project=<id>` — project-scoped, recent jobs for that project.

**The five `/__*` conversions:** each now enqueues and answers **202 `{ jobId }`** instead of proxying inline. Ownership, key and cap checks stay exactly where they are — they gate the enqueue. `/__export-download`, `/__regen-revert`, the overrides, plan and archetypes endpoints are untouched.

**A project can now exist with an empty directory** (created at enqueue, filled by the job). The preview pool will be asked to spawn a child for a directory with no `vite.config.ts` — it must fail legibly rather than time out. Check what `startPreviewServer` does today (it throws a clear "No vite.config.ts found" error) and make sure that surfaces as a clean 4xx/5xx with a useful message, not a 60s spawn timeout.

**In `serve.ts`**, preserving its load-bearing order: after `openDatabase` and adoption, call `markRunningJobsInterrupted` and log the count; construct and `start()` the worker; `stop()` it in the existing `SIGINT`/`SIGTERM` shutdown alongside `pool.shutdown()`.

**Delete the registry's session-only-billable skip.** It exists as a visible placeholder for exactly this endpoint; once `POST /api/generate` is billable and session-only, the enforcement table covers it for real and the skip must go — not be left passing vacuously.

Tests: 202 with a job id from each converted endpoint; over-cap still 402 at enqueue and no job row created; another user's job id → 404; `GET /api/jobs/:id` returns the terminal status and result; a project row and directory exist immediately after `POST /api/generate`; the partition and billable-enforcement tests still hold with the new entries.

Commit: `feat(server): enqueue long-running work and expose job status`.

### Task 4: The editor

**Files:** modify `editor/src/App.tsx`; add `editor/src/lib/jobs.ts` + test; update the affected `editor/e2e/*.spec.ts`.

One helper — `enqueueAndPoll(url, body, { onStatus })` — that POSTs, reads `{ jobId }`, polls `GET /api/jobs/:id` every 2s, and resolves with the terminal job or rejects with its error. Five call sites adopt it: regen, page regen, add-section, edit-prompt, export.

**The UI loses fine-grained progress and must say so honestly**: show "running" plus elapsed time, not a fabricated percentage. Where a progress line exists today, replace it with the elapsed-time state rather than deleting the affordance.

**Handle `interrupted` explicitly.** It is not a synonym for failure: the work may have completed. The message must say the outcome is unknown and to check the page — inventing "failed" would be a lie a user acts on.

The milestone-7 e2e specs assert the synchronous flows. Update them to the enqueue-and-poll shape; **do not weaken what they assert about the outcome** — the section still has to appear, the override still has to survive. If an assertion cannot be preserved, stop and report rather than dropping it.

Commit: `feat(editor): submit long-running work as jobs and poll for the outcome`.

### Task 5: Verify against a real run

Unit tests stub the pool and the proxy, so nothing yet proves a job actually runs. With `WG_REGEN_MOCK=1` (no model spend):

1. Create a user, store a key, start the server.
2. `POST /__regen?project=<id>` → 202 + job id; poll to `succeeded`; confirm the section changed on disk.
3. Restart the server while a job is `running`; confirm it comes back `interrupted`, not `running` or `succeeded`.
4. Set the cap to 0; confirm enqueue is refused with 402 and **no job row is created**.
5. A second user polling the first user's job id → 404.
6. `POST /api/generate` with a brief → 202, a project row and directory exist immediately, and the job progresses. If a real generation is affordable, run one and report the ingested `usage_event` rows and cost; **if not, say plainly that generation is proven only in mock mode** rather than implying otherwise.
7. Confirm no orphaned node/vite process holds a port afterwards.

Report every result verbatim, including anything that did not behave as expected.

## What this slice deliberately does not do

1. **No retry, backoff, or dead-letter queue.** A failed job is failed; the user resubmits. Automatic retry of model work is how a spend cap gets defeated.
2. **No cancellation.** The subprocess cannot be safely killed mid-run (spec decision 13), so a cancel button would either lie or corrupt a page.
3. **No fine-grained progress.** Recovering it later is additive — an SSE endpoint or a `progress` column — and is not built now.
4. **No cross-process worker.** One loop; the pool's cap of 6 is the real limit anyway.
5. **The editor is wired to the hosted server for the first time here.** `PREVIEW_URL` defaulting to `http://localhost:5273` and every `/__*` call lacking `?project=` are this slice's problem to solve, and the local unauthenticated preview must keep working unchanged.
